# 最適化 UI 設計書

イベント会場ブース配置最適化(NSGA-II)の入力設定と、
最適化中の解の GUI 確認を行う Web UI(Streamlit)。

`src/` の最適化・シミュレーション・可視化、`scripts/` のCLI、`ui/` の
Web画面は同じ直接配置NSGA-II実装を共有する。配布ZIPはこれらと設定ファイルを
まとめて含み、`real_world_problem/` ディレクトリ単位で置き換えられる。

---

## 1. 要件と対応

| 要件 | 対応 |
| --- | --- |
| 入力: イベント会場のサイズ | サイドバー「会場」。矩形モードで幅・高さ・入退場辺を指定 |
| 入力: ブースのサイズ・数 | サイドバーのブース表(`st.data_editor`)。行の追加・削除で数を変更 |
| 入力: エージェント数 | サイドバー「来場者・シミュレーション」→ エージェント数 |
| 入力: シミュレート時間 | 同上 → シミュレート時間(秒)。到着プロファイルも自動で伸縮 |
| 入力: 世代数・探索個体数 | サイドバー「最適化(直接配置NSGA-II)」 |
| 新方式の探索設定 | 完全ランダム初期集団を使用。整然性制約、3段階突然変異、Memetic探索は内部既定値を使用 |
| 出力: 最適化中の解を選択 | パレート図の点をクリックして選択 |
| 比較: 実会場で実際に使われた配置 | `booths.yaml` の `fixed_position` を評価し、★ でパレート図に重ねる |
| 出力: 10 世代ごとに GUI 表示 | スナップショット間隔(既定 10)ごとに集団を保存し、世代スライダで切替 |
| 表示: 会場レイアウト図 | タブ 1。`src/visualization.py::draw_venue` を再利用 |
| 表示: 混雑ヒートマップ | タブ 2。`plot_heatmaps` を再利用 |
| 表示: エージェント動画 | タブ 3。`render_animation`(GIF)を再利用 |

## 2. 全体構成

最適化は **別プロセス** で回す。理由は 2 つ。

1. `multiprocessing.Pool` は Windows では spawn 方式のため、Streamlit の
   アプリスクリプト内から起動すると `app.py` が再 import されて破綻する。
2. 最適化は数分〜数時間かかる。UI プロセス内で回すと画面が固まり、
   ブラウザを閉じると計算も消える。

UI とワーカーは共有メモリを持たず、**実行ディレクトリ配下のファイルだけ** で
やり取りする。ブラウザを閉じても最適化は走り続け、後から同じ実行を開ける。

```
┌─────────────────────────┐          ┌──────────────────────────────┐
│ Streamlit (ui/app.py)   │          │ ワーカー (ui/optimize_worker.py) │
│                         │          │                              │
│ サイドバー入力          │  起動 →  │ load_config(run_dir/config)  │
│   ↓ RunParams           │          │   ↓                          │
│ build_config_dir()      │  ──────→ │ run_direct_nsga2(…)          │
│   → run_dir/config/*.yaml│         │   ↓ 毎世代                    │
│                         │          │   status.json を更新          │
│ 2秒ごとポーリング       │ ←──────  │   ↓ N世代ごと                 │
│   status.json           │          │   snapshots/gen_NNNN.json    │
│   snapshots/*.json      │          │   ↓ 終了時                    │
│   ↓                     │          │   save_results(results/)     │
│ パレート図(クリック選択)│          └──────────────────────────────┘
│   ↓ 設計ベクトル x      │
│ evaluate_layout() で再現 │  ← 可視化のみ UI プロセス内で実行
│   → 図 / ヒートマップ / GIF │
└─────────────────────────┘
```

### 実行ディレクトリ

```
real_world_problem/runs/<run_id>/       run_id = YYYYMMDD_HHMMSS
├── params.json          UI の入力値そのまま(再現・再実行用)
├── config/              ワーカーが load_config() で読む YAML 3 点
│   ├── default_config.yaml
│   ├── booths.yaml
│   └── visitor_profiles.yaml
├── status.json          進捗。毎世代更新。UI のポーリング対象
├── fixed_layout.json    実会場配置(booths.yaml の fixed_position)の評価結果
├── snapshots/
│   ├── gen_0001.json    第 1 世代(初期集団)
│   ├── gen_0010.json    以降 snapshot_interval ごと
│   └── ...
├── results/             パレート解・代表解・直接配置方式のメタデータ(任意)
├── ui_cache/            可視化した PNG / GIF のキャッシュ
└── worker.log           ワーカーの標準出力・標準エラー
```

**設定は YAML 経由。** UI は `Config` を直接組み立てず、プリセット YAML を
読んで編集項目だけ上書きし、実行ディレクトリに書き出す。
`src/models.py::load_config` はそのディレクトリを読むだけなので、
ローダにもスキーマにも変更が不要。README §26 の「設定は YAML で一元管理」も守られる。

### スナップショットの形式

```json
{
  "generation": 10,
  "n_generations": 100,
  "elapsed_seconds": 312.4,
  "n_solutions": 14,
  "solutions": [
    {"x": [17, 11, 1, ...], "f_move": 82.31, "f_congestion": 0.00041, "rank": 0}
  ]
}
```

環境選択後の集団のうち、**実行可能(g ≤ 0)かつ目的関数値が有限** な個体のみを
設計ベクトル重複除去のうえ `f_move` 昇順で保存する。
`rank == 0` が非支配解(その世代のパレートフロント)。

設計ベクトル `x` をそのまま持たせているので、UI 側で
`to_integer_layout(x, cfg)` → `apply_layout` → `evaluate_layout` により
任意の世代の任意の解をいつでも再現できる。乱数は §2.3.2 の 3 系統分離方式で
配置に依存しないため、ワーカーでの評価と UI での再評価は完全に一致する。

### 比較基準(実会場で実際に使われた配置)

`config/booths.yaml` の各ブースが持つ `fixed_position: [x, y, theta]` は、
調布市マルシェで実際に使われた配置。ワーカーは**最適化を始める前に**
これを最適化解と同じ条件で 1 回シミュレーションし、`fixed_layout.json` に残す。
UIのブース編集表では `fixed_position` を表示せず内部列として保持し、実行用の
`booths.yaml` へ引き継ぐ。したがって、実会場モードの新規実行でも比較基準が失われない。

```json
{
  "available": true,
  "label": "実会場配置(booths.yaml)",
  "feasible": true,
  "violation": 0.0,
  "positions": [[17, 11, 1], ...],
  "x": [17, 11, 1, ...],
  "f_move": 37.625,
  "f_congestion": 0.085,
  "timed_out": false
}
```

- **最適化より先に評価する。** 第 1 世代のスナップショットが出た時点で
  パレート図に重ねられるようにするため。
- **タイムアウトだけ緩める**(`replace(cfg, timeout_seconds=3600)`)。
  比較基準が §17.6 の打ち切りでペナルティ値になると意味がない。
- **失敗しても最適化は止めない。** `scripts/run_optimization.py` は
  制約違反で `ValueError` を投げるが、UI では `available: false` と
  理由を記録して続行する。制約違反の場合はシミュレーション自体は行い、
  「参考値」と明示したうえで表示する。
- **矩形会場モードでは作らない。** `fixed_position` は実会場ポリゴンの
  座標系を前提としており、`build_config_dir` が矩形モードでは落とすため。

`x`(設計ベクトル)をスナップショットの解と同じ形で持たせてあるので、
比較基準もパレート図でクリックでき、レイアウト図・ヒートマップ・
アニメーション・推移比較のすべてで通常の解と同じように扱える。

### 更新モデル

- 進捗パネルだけを `@st.fragment(run_every=2.0)` で 2 秒ごとに再実行する。
  ページ全体は再実行されないため、**パレート図のクリック選択が消えない**。
- 世代スライダの選択肢は保存済みスナップショットから生成する。
  新しい世代を見たいときは「最新世代へ」ボタンで全体を再実行する。

### 解の選択(A/B スロット)

`st.plotly_chart(on_select="rerun", selection_mode="points")` を使う。
各点の `customdata` にスナップショット内のインデックスを埋めてあるので、
クリックイベントからそのまま解 1 件を引ける。

Streamlit の plotly 選択はクリックのたびに選択が**置き換わる**ため、
修飾キーによる多点選択ができない。そこでクリックを 1 件ずつ受け取り、
A → B の順に 2 スロットへ溜める(3 つ目のクリックで古い A が押し出される)。
選択中の点は**別トレースを重ねるのではなく、既存トレースの点ごとの
枠線と A/B ラベル**で表す。重ねたトレースはクリックを横取りして
選択を壊すため。

比較基準(★)には `customdata = -1` を割り当ててあり、通常の点と同じく
クリックして A/B に入れられる。世代を切り替えるとスロットは破棄されるが、
比較基準は世代に依存しないので残る。

### 比較基準の表示

パレート図の上に、実会場配置に対する要約を出す。

- 実会場配置の `f_move` / `f_congestion`
- **両目的とも実会場配置より小さい解の数**(= 実会場配置を支配する解)
- そのうち改善率の合計が最大の解と、その改善率

図の上では ★(緑)のマーカーと、そこから伸びる縦横の破線で表す。
破線があると「★ より左下の領域＝両目的で改善した解」が一目で分かる。

選択した解の metric には、実会場配置に対する増減を `delta` として出す
(目的関数は小さいほど良いので `delta_color="inverse"`)。

### 可視化の実行タイミング

| 表示 | シミュレーション | 実行契機 |
| --- | --- | --- |
| 会場レイアウト図 | 不要(配置を描くだけ) | 選択と同時に自動 |
| 混雑ヒートマップ | 1 回必要 | ボタン押下時 |
| エージェント動画 | 1 回 + GIF 生成 | ボタン押下時 |

レイアウト図だけ即時、重い 2 つはボタン押下にしてある。
クリックのたびにシミュレーションが走ると UI が使い物にならないため。
生成物は設計ベクトルの SHA-1 をキーに `ui_cache/` へ保存し、
`st.cache_data` と併せて二重にキャッシュする。

可視化用のシミュレーションでは `timeout_seconds` を 3600 秒に置き換える
(`dataclasses.replace`)。最適化中は §17.6 の打ち切りが必要だが、
可視化で途中打ち切りになると図が意味をなさないため。

## 4. 入力パラメータの扱い

### 会場サイズ

会場形状の指定方法が 2 通りあるため、モードで分ける。

- **矩形モード** — 同梱した `config/` を基に `venue_shape` を落とし、
  `grid.width/height` と入退場辺だけで会場を決める。
  会場サイズを自由に変えられる。ブースの `area`(広場所属)と
  `fixed_position` は落とす(広場が存在しないため制約が成立しない)。
- **実会場モード** — `config/default_config.yaml` の `venue_shape`
  (多角形の広場・道路・障害物)をそのまま使う。頂点座標がメートル固定なので
  グリッドサイズは変更不可とし、UI では読み取り専用で表示する。

> 実会場の形状を変えたい場合は `config/default_config.yaml` の
> `venue_shape` の頂点を直接編集する。UI からポリゴンを編集する機能は、
> 会場定義がコードでなく設定ファイルにある現在の構成を崩さないため入れていない。

### シミュレート時間と到着プロファイル

`duration_seconds` を変えると `arrival_profile` の区間と食い違うため、
プリセットの形状比率を保ったまま時間軸を線形に伸縮する
(`run_store._rescale_arrival_profile`)。
例: `[[0,60,1.6],[60,180,1.1],…]` を 400 秒 → 800 秒にすると
`[[0,120,1.6],[120,360,1.1],…]` になる。

### ブース数

ブース表の行数がそのままブース数になる。`booth_id` は保存時に 0 起点で
振り直す(`run_store._normalize_booths`)。設計変数は
通常ブースは `(x, y, θ)` の3変数、方向を持たないテーブルは `(x, y)` の2変数。
したがって行数やテーブル数を変えると探索空間の次元も変わる。

## 5. 使用する最適化方式

UIワーカーは `src.direct_optimization.run_direct_nsga2()` を呼び、CLIと同じ
単一レベル直接配置方式を使用する。

- 初期集団は `prepare_random_feasible_direct_population()` により、固定配置や
  列テンプレートを使わず、物理制約だけを満たす完全ランダム配置として生成する。
- 第30世代までは突然変異率を0.90、局所・中規模・大域の選択率を
  `0.20 / 0.30 / 0.50` とし、以後は `0.70`、`0.55 / 0.30 / 0.15` へ戻す。
- 大域突然変異は、互いの配置距離を確認した最大32個の整然配置ドナーを使う。
  プール満杯後も確率的にドナーを更新する。
- NSGA-IIの環境選択では目的関数のrank/crowdingを優先したうえで、配置距離が
  0.02未満の近似重複を後回しにする。個体数が不足する場合は後回し個体を戻す。
- Memetic局所探索は第29世代まで停止し、第30世代以降に指定間隔で実行する。
- ブース正面幅全体×奥行き2セルの空間を物理制約として常時確保する。
  正面空間同士は共用できるが、他ブースの本体・受付・退出口・待機列は
  侵入できない。列・外周構造、整列誤差、間隔、方向、孤立は説明用に記録する。
  方向と出入口を持たないテーブルには、方向・正面通路の評価を適用しない。
- 終了時は通常の成果物に加え、`direct_*_designs.csv`、
  `direct_*_method.json`、`memetic_history.csv`、`mutation_history.csv`、
  `orderliness_schedule_history.csv`、`layout_diversity_history.csv` を保存する。

UIの探索設定は `runs/<run_id>/params.json` に保存されるため、評価シードとは別の
最適化シードも含めて再現できる。初期集団は個体ごとの決定的な乱数系列を使うので、
並列プロセス数を変えても同じ設定・同じ最適化シードなら同一になる。

## 6. 使い方

```bash
pip install -r requirements.txt          # streamlit, plotly が追加されている
cd real_world_problem
streamlit run ui/app.py
```

ブラウザが開いたら、サイドバーでパラメータを設定して「最適化を開始」。

- 進捗バーが動き出したら、スナップショット間隔ごとに世代スライダの
  選択肢が増えていく。
- パレート図の点をクリックすると、右側にその解のレイアウト図が出る。
- ヒートマップ・アニメーションは各タブのボタンで生成する。

ワーカーが失敗した場合は進捗パネルにトレースバックが出る。
詳細は `runs/<run_id>/worker.log` を見る。

## 9. 設計上の判断

1. **最適化をサブプロセスに分離** — Windows の spawn 対応と、
   ブラウザを閉じても計算が継続することの両立。
2. **ファイル経由の通信** — キューやソケットを使うと Streamlit の
   再実行モデル(スクリプト全体が毎回走る)と相性が悪い。
   ファイルなら過去の実行をそのまま開き直せる副次的な利点もある。
3. **スナップショットに設計ベクトルを保存** — 目的関数値だけを保存すると
   後から配置を再現できない。ベクトルさえあれば UI 側で何度でも再評価できる。
4. **可視化は UI プロセスで実行** — ワーカーで全解の図を作ると
   最適化が遅くなる。見たい解だけを、見たいときに評価する。
5. **重い可視化はボタン押下** — クリックのたびにシミュレーションが
   走らないようにする。
6. **プリセット YAML の上書き方式** — `Config` を UI から直接組み立てると
   `load_config` と二重管理になる。YAML を経由すれば設定の入口は 1 つのまま。
